Public Key Infrastructure (PKI)

Hierarchical Certificate Trust Chain

How web browsers establish trust by traversing digital signatures from the website certificate back to a trusted Root CA.

Level 1 • Root CA

Root Certificate Authority (Root CA)

Self-signed Trust Anchor pre-installed in OS/browser certificate store (e.g. GTS Root R1, DigiCert Root).

Digital Signature: Self-signed
Digitally signs with private key
Level 2 • Intermediate CA

Intermediate Certificate Authority

Acts as a proxy issuer to isolate the Root CA's private key from operational network exposure.

Signed by: Root CA
Digitally signs website public key
Level 3 • End-Entity (Leaf)

Website Certificate (*.google.com)

Issued specifically to the domain name. Binds the website's public key to its fully qualified domain name.

Signed by: Intermediate CA
Browser validates signatures up to Root
Level 4 • Client Browser

User Browser / Operating System

Validates the chain. If any signature fails or the Root is unknown, the browser alerts: "Connection is not private".

Network Protocol Workflow

How HTTPS Works: The TLS Handshake

A step-by-step cryptographic walk-through showing how an insecure TCP channel is transformed into an encrypted, tamper-resistant tunnel.

1
Client → Server

Client Hello

The browser initiates the handshake by sending its supported TLS versions (e.g. TLS 1.3, 1.2), a list of supported cipher suites, and a random byte string called the Client Random.

Concept: Protocol Negotiation & Random Nonce
2
Server → Client

Server Hello & Digital Certificate

The web server selects the highest mutually supported TLS version and cipher suite (e.g., TLS_AES_256_GCM_SHA384), sends its own Server Random, and transmits its X.509 Digital Certificate containing its Public Key.

Concept: Authentication via Digital Certificate
3
Client Validation

Certificate Verification & Asymmetric Key Exchange

The browser checks the certificate against its local trusted CA store (valid dates, SAN matching, signature validity). Both client and server exchange public key parameters using ECDHE (Elliptic Curve Diffie-Hellman Ephemeral) to compute a shared secret without ever transmitting it across the network!

Concept: Public-Key Cryptography & Forward Secrecy
4
Client & Server

Derivation of Symmetric Session Keys

Using the shared secret and random nonces, both parties independently derive matching Symmetric Session Keys (e.g., 256-bit AES keys). Asymmetric encryption is now complete!

Concept: Symmetric Key Derivation for High Speed
5
Bidirectional

Finished & Secure Symmetric Encrypted Communication

Both send an encrypted Finished message verifying that the handshake was not tampered with. All subsequent HTTP requests and responses (passwords, cookies, HTML) are encrypted using fast symmetric AES-GCM or ChaCha20-Poly1305.

Result: Confidentiality • Integrity • Authentication
Syllabus Guide

Understanding Core Cryptography Concepts

Simple, easy-to-understand explanations of the 10 fundamental Cryptography & Network Security topics demonstrated in this project.

01

HTTPS (HTTP Secure)

HTTPS is the secure version of HTTP. It wraps normal plaintext web communication inside an encrypted TLS/SSL tunnel on port 443, ensuring attackers cannot intercept passwords or modify web content.

02

TLS (Transport Layer Security)

The cryptographic protocol succeeding SSL. TLS provides three core security guarantees: Confidentiality (encryption), Integrity (tamper detection), and Authentication (identity verification).

03

Digital Certificate (X.509)

An electronic passport for a website. It binds the server's public key to its domain name and is signed by a recognized Certificate Authority so browsers know the site is authentic.

04

Public Key Cryptography (Asymmetric)

Uses a pair of keys: a Public Key (freely shared with the world) and a Private Key (kept secret by server). Data encrypted with the public key can only be decrypted with the private key.

05

Symmetric Encryption

Uses a single shared key for both encryption and decryption (e.g. AES-256-GCM). Because symmetric ciphers are computationally much faster than asymmetric ciphers, they are used for bulk data transfer.

06

Cryptographic Hashing (SHA-256)

A one-way mathematical function transforming input data of any size into a unique fixed-length digest. Any modification to the data completely alters the hash (avalanche effect), enabling tamper detection.

07

Digital Signature

A mathematical technique that guarantees authenticity and non-repudiation. A CA hashes the certificate details and encrypts that hash with its private key. Browsers decrypt it with the CA's public key to verify integrity.

08

Certificate Authority (CA)

A mutually trusted third-party organization (such as DigiCert, Let's Encrypt, or Google Trust Services) that verifies domain ownership and issues digital certificates forming the Root of Trust.

09

Server Authentication

Confirms that the user is really connecting to the genuine server and not an impersonator. It prevents Man-in-the-Middle (MitM) attacks where an attacker tries to intercept unencrypted traffic.

10

Confidentiality & Integrity

Confidentiality: Only the sender and intended recipient can read the data. Integrity: Detects if any bit of data was altered or replayed by an attacker during transmission.

Examiner Q&A

Viva Voce Preparation & Project Info

Common questions college professors and examiners ask during Cryptography project presentations.

Q1

Why does HTTPS use both Asymmetric and Symmetric cryptography?

Asymmetric encryption (RSA/ECDHE) is computationally slow and resource-heavy, but it solves the key distribution problem (it allows two strangers to securely agree on a key). Symmetric encryption (AES) is extremely fast. Therefore, HTTPS uses asymmetric cryptography during the handshake to exchange keys, and symmetric cryptography for encrypting actual web data.

Q2

What is Perfect Forward Secrecy (PFS)?

PFS ensures that even if an attacker steals the server's private key in the future, they cannot decrypt past recorded web sessions. Modern TLS achieves PFS using ephemeral Diffie-Hellman (ECDHE), where keys are uniquely generated per session and discarded immediately.

Q3

What happens if a digital certificate expires?

Browsers check the notAfter timestamp against the local clock. If the current time is past expiration, the browser terminates trust and issues an SSL warning (e.g., ERR_CERT_DATE_INVALID), preventing users from entering credentials.

Q4

Why are Intermediate CAs used instead of signing directly with Root CAs?

To protect the Root CA's private key. The Root CA remains completely offline and in a secure physical vault. If an Intermediate CA is ever compromised, it can be revoked without invalidating the entire global Root CA trust store.
